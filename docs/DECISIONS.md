# Architectural & Product Decisions Log (DECISIONS.md)

This log records all key technical and product decisions, context, and rationale for the AI Healthcare Receptionist system.

---

## DEC-001: Patient Verification Strategy
- **Context**: Patients accessing sensitive appointment details, canceling, or rescheduling must be authenticated without imposing complex login portals or SMS OTP overhead over Telegram.
- **Decision**: Two-factor matching combining a unique 6-character alphanumeric booking code (e.g. `APT-8F2B`) and the patient's phone number or name provided at booking.
- **Security Control**: Enforce a maximum of 3 failed verification attempts per chat session. If exceeded, the session is locked for 15 minutes and an automatic escalation ticket is logged for staff review.
- **Rationale**: Balances zero-friction access on Telegram with privacy protection, ensuring patients can only inspect or modify their own appointments.

---

## DEC-002: Clinic Manager Authentication & Linking
- **Context**: The Telegram bot must distinguish between regular patients and authorized clinic managers without public sign-up or hardcoded Telegram user IDs.
- **Decision**: Single-use, cryptographically secure 8-character invite codes generated by the backend (`InviteCode` table). A manager links their Telegram account by sending `/link <INVITE_CODE>`.
- **Security Control**: Upon successful linking, the Telegram ID is bound to the clinic with role `MANAGER`, the invite code is marked used, and all future requests from that Telegram ID are scoped exclusively to that clinic ID.
- **Rationale**: Simple, zero-leak mechanism suitable for clinic staff who are non-technical, while guaranteeing complete clinic boundary isolation.

---

## DEC-003: Bot Deployment Architecture (One Bot vs Many Clinics)
- **Context**: Should each clinic run its own Telegram bot or should a single bot serve multiple clinics?
- **Decision**: Single Telegram Bot architecture with multi-tenant data isolation.
- **Routing Mechanism**:
  - The bot operates with a configured default clinic (`clinic_default` / Demo Clinic) for direct walk-in interactions.
  - Deep-link support allows clinics to share `t.me/<bot_username>?start=clinic_<clinic_id>` or `/clinic <clinic_id>`, binding the user session to that specific clinic.
- **Rationale**: Drastically reduces deployment and operational overhead (single webhook, single bot token, single ngrok tunnel) while keeping clinic data strictly separated at the database and API authorization layers.

---

## DEC-004: Escalation Routing & Notification
- **Context**: When an inquiry is out of administrative scope, medical in nature, or fails verification, where does the escalation go?
- **Decision**:
  1. Escalation record persisted in the backend database (`Escalation` table) with query context, patient ID, and timestamp.
  2. Immediate Telegram alert dispatched to all linked `MANAGER` / `STAFF` Telegram IDs for that clinic.
  3. Structured JSON log emitted with level `WARN` and `escalation: true` for auditability.
- **Rationale**: Gives clinic staff immediate, actionable notification within Telegram without requiring them to monitor a separate dashboard 24/7.

## DEC-005: LLM Provider and Model Selection
- **Context**: The agent needs high-speed multilingual comprehension (Hindi, English, Hinglish), reliable JSON schema adherence, and low latency for chat responses.
- **Decision**: Google Gemini 2.5 Flash (`gemini-2.5-flash`) via the Google GenAI SDK / LangChain integration.
- **Rationale**:
  - Extremely fast response times (typically <1.2 seconds), critical for chat UX.
  - Superior native performance on Indian languages (Hindi Devanagari and Romanized Hinglish).
  - Robust structured JSON output for tool calling and document draft extraction.
  - Active verified API key present in `.env`.

## DEC-007: Confirmation State Machine & Concurrency Control
- **Context**: Requirement: 100% of bookings, cancellations, and reschedules must be preceded by explicit patient confirmation. Double bookings must be impossible.
- **Decision**:
  1. LangGraph workflow uses native `interrupt()` nodes before executing state changes, guaranteeing that the LLM cannot bypass user confirmation.
  2. The backend appointment endpoint requires a valid `confirmation: { confirmed: true, confirmationId }` payload AND an `idempotencyKey` header.
  3. PostgreSQL partial unique index on `(doctor_id, starts_at) WHERE status = 'BOOKED'` guarantees atomic concurrency safety against race conditions.
